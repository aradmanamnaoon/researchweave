# AI retrieval and agent planning (§40.92–40.96)

The AI crate now exposes `assistant.retrieval.index` (LocalWrite), `assistant.retrieval.search` (Read), and `assistant.agent.plan` (Read). Host integration is now present: the CLI opens `<data-root>/ai-grounding.json`; the desktop opens `<project>/data/assistant-grounding.json`; both attach the store with `AiOperationHandler::with_grounding` and register the shared AI capability manifest through `CommandRouter`.

The host supplies indexed passages with explicit `citation_id`, `source_id`, `revision`, and content. Indexing does not crawl files or contact any provider. Entries are isolated by dispatch project ID; duplicate citation IDs replace existing entries in the same project. Storage uses bounded JSON snapshots and a same-directory atomic file replacement; the host must coordinate concurrent processes and select a private directory. The lexical search is deterministic and case-insensitive, ranks by the number of matching query terms with citation-ID tie breaking, and returns matching content with provenance identifiers. Limits: 2,048 entries/project, 16,000 UTF-8 bytes/passage, 16 MB total snapshot, 512-byte query, 1–20 hits, and 1–32,000 UTF-8 bytes returned content. It does not invent citations or retrieve records from other projects. Semantic embeddings, incremental indexing, content revocation and source-level authorization remain host integration work; indexes should be regenerated or invalidated when source revisions change.

assistant.agent.plan validates an explicit goal and up to 16 tool proposals, emits ordered steps marked proposed, approval_granted=false, and requires_router_dispatch=true, and never executes or approves operations. Approved execution is now handled by the separate trusted-host AgentActionStore: it persists the exact command and fingerprint, records the human decision, and only then dispatches that unchanged command through the shared router's independent one-use approval and audit boundary. The planner remains deterministic formatting of host-supplied proposals rather than autonomous AI reasoning. Its arguments can contain research text and must be treated as untrusted/private by the host; local plan construction does not transmit it.

Tests cover project isolation, restart persistence, bounded retrieval, invalid queries, no incidental provider access, deterministic plans and inert proposals. After host attachment, AI tests remain **19/19**, CLI tests **3/3**, and desktop tests **17/17**. The CLI host regression additionally dispatches `assistant.retrieval.search` through the real router against a newly opened durable store and receives `status=ok`, an empty result set and `no_external_search=true`. The compiled capability snapshot includes all three new operations. Native GUI retrieval interaction, semantic embeddings, stale-source invalidation/source authorization and a full autonomous §40.94–40.96 tool lifecycle are still not claimed; plan steps remain inert until separately dispatched through the shared approval/audit router.

## Source withdrawal follow-up

`assistant.retrieval.revoke_source` is now a `LocalWrite` capability. The caller supplies exactly `{"source_id":"..."}` and the dispatch project ID provides scope. Preview validates inputs and reports intent without changing data; execution is routed through standard local-write approval/audit. On approval the grounding store atomically persists removal of every matching citation from that source in the current project. Repeated revocations return `revoked_passages: 0`, and sources indexed into other projects remain searchable. This permits a host to withdraw a source after deletion or an authorization change. It is not an automatic event listener: hosts must issue revocation when a source changes and reindex newly authorized revisions. Source-level access checks and automatic stale-revision detection are still pending.
