## Persistent storage, migration and recovery

The current native SQLite project schema advances **v5 to v6**. Fresh projects have the new `manuscript_comments` table, source revision composite foreign key to existing immutable `manuscripts(id,section,revision)`, section/revision indexes, and SQLite `BEFORE UPDATE` and `BEFORE DELETE` abort triggers. Each comment has a UUID, exact source manuscript ID, section and section revision, source body SHA-256, Unicode scalar start/end, byte-exact quote, reviewer, comment, actor, recorded timestamp and project revision. No old manuscript rows or event rows are rewritten.

`inspect_schema` advertises v5 as upgradeable; `migrate_project` uses the existing verified pre-migration SQLite backup and atomic schema transaction, registers migration 6, and preserves earlier migrations 0–5. V6 projects without the comment table/index/immutability triggers are invalid, not silently accepted. Existing archive verification accepts earlier archive reader schemas; prior RWENC1 envelope crypto and object/archive formats are untouched. As with earlier native migrations, callers must explicitly run the project migration gate before opening an old project through `ProjectStore::open`. Migrated v5 and trigger-tampering test cases are included in the owned project crate.

**P1 migration correction (verified):** the legacy `execute_static_sql` helper splits DDL on semicolons, which cannot parse SQLite `CREATE TRIGGER ... BEGIN SELECT RAISE(...); END;` bodies. The v6 branch now uses `transaction.execute_batch(MANUSCRIPT_COMMENTS_SCHEMA_V6_SQL)` on the whole trusted static DDL **inside the existing `TransactionBehavior::Immediate` migration transaction**. Older migrations retain their original execution behavior. A new v5→v6 test inserts an anchored synthetic row after migration and exercises both real `UPDATE` and `DELETE` trigger aborts, checks that its original comment remains unchanged, confirms the pre-migration backup is v5 and integral, and checks idempotent reopening.

## Native API operations

| Operation | Effect | Required scope and checks |
|---|---|---|
| `writing.comment_preview` (also `preview("writing.comment_record",...)`) | Read only | Exact project UUID and trusted path; mandatory `DispatchContext.expected_revision`; active/latest source section revision; supplied source body SHA-256; Unicode scalar quote span; reviewer/comment limits; nonoverlapping persisted comment anchor |
| `writing.comment_record` | Local write, user approval required | A NEW trusted request ID is permitted; exact same project, actor, CAS, comment and source as Preview; mandatory `approved_preview_sha256` returned by preview; recheck *inside* transactional native event mutation; append immutable row and canonical event hash; increment project revision once |
| `writing.comment_list` | Read only | Exact project/section, bounded to at most 1000 records; reports `current`, `historical_source_revision` or `invalid_source_anchor` without automatic relocation; displays saved reviewer/quote/comment only to explicit authorized local read |

Recommended arguments: `project_id`, `manuscript_id`, `section`, `source_revision`, `source_body_sha256`, `start_scalar`, `end_scalar`, `quote`, `reviewer`, `comment`; then pass `approved_preview_sha256` to the explicit approved record request with the **same trusted project ID, actor and expected project revision, but a fresh command request ID**. The desktop host creates one request ID for preview and another for approved execution, so the digest must NOT bind that ephemeral request ID. Instead it binds project, actor, revision, source, quote, reviewer and comment. The project CAS, uniquely recorded request ID/event chain, and independent one-use host approval enforce the actual write boundary. **The digest is not a cryptographic signature, a secret token, or proof of human review.** The host must display the proposal and enforce actual human consent before forwarding it. No UI/desktop wiring was added in this slice.

Boundaries: manuscript ID ≤128 UTF-8 bytes, section ≤160 Unicode scalar values, positive latest source revision, lowercase 64-digit source SHA-256, `0 ≤ start_scalar < end_scalar ≤ 1,000,000`, quote ≤2,048 scalars with exact slicing of the persisted immutable body, reviewer ≤160 scalars/640 bytes, comment ≤4,000 scalars/16,000 bytes. Null bytes and blank reviewer/comment are rejected. Unicode scalar positions differ from bytes and grapheme clusters; callers must not pass UTF-16 code-unit indices directly. Overlapping annotations on the **same source revision** deliberately fail closed; disjoint comments are separately appendable.

## Privacy, audit and no silent editing

- Neither a preview response nor the event-chain payload exposes reviewer text, quoted text or comment content; instead it records SHA-256 digests and bounded metadata. The private SQLite comments table contains the actual comment for authorized explicit retrieval. No network access, model-generated review or external verification is performed.
- The event-chain/CAS transaction enforces a never-replayed request ID and expected project revision; both source revision/body digest and quote span are rechecked atomically immediately before the append. A newer manuscript revision or project mutation invalidates the pending preview.
- The manuscript body and citations are never altered by a comment write. The list operation does not guess where an old quote moved; it marks a historical revision or an invalid source anchor.
- Appends are irreversible through this first API; deleting/editing comments would require a future separately audited compensating-record feature. The SQL triggers protect against accidental direct updates/deletes through the current database connection, not a malicious attacker with filesystem ownership who can replace the entire project.
