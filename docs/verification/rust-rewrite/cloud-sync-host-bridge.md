# Cloud sync host bridge and profile persistence (2026-10-25)

The Rust cloud layer now exposes routed encrypted sync operations for a project snapshot: `cloud.sync.push`, `cloud.sync.pull`, `cloud.sync.tip` and `cloud.sync.history`. Push accepts only an existing verified `.rwproj` whose authenticated project identity matches the command scope. The sync engine encrypts the archive before it reaches the revision backend, uses conditional compare-and-swap tip updates, and preserves a divergent encrypted revision on conflict. Pull decrypts into memory, writes a temporary file under the chosen destination parent, verifies the complete `.rwproj` and project identity, then persists with no-clobber semantics.

S3 credentials and project encryption secrets have separate stores. `OsKeyringStore` keeps access/secret/session credentials under the S3 keyring service. `OsSyncSecretStore` keeps project-scoped sync passphrases under `org.researchweave.sync-encryption`; retrieved strings are wrapped in `Zeroizing`. Routed `cloud.encryption.store/delete` operations never return the passphrase. Capability manifests mark S3 credentials and sync passphrases as sensitive arguments.

Cloud profile metadata is durable without storing secrets in the profile file. `CloudOperationHandler::with_profile_path` loads a strict versioned JSON file, validates every S3 profile, rejects duplicate identifiers/symlinked profile files and persists sorted updates through a temporary file. `cloud.profile.list` reports non-secret metadata plus whether a keyring entry is present. `cloud.profile.disconnect` removes the profile and revokes verified backend capability while intentionally leaving credentials untouched; credential deletion remains an explicit separate command. The CLI uses `<data-root>/cloud-profiles.json`, so configured profile metadata survives process restart.

Focused tests use the real revision engine with a memory backend to prove encrypted push/pull, deterministic project scoping, create-new pull, and conflict preservation. A restart test proves profile configure/update/list/disconnect persistence while asserting the JSON file never contains credential sentinel strings. Cloud tests 13/13 and CLI tests 2/2 pass with warnings-denied Clippy.

The desktop now exposes Cloud Sync through the native Slint workbench: profile configuration, OS-keyring credential storage/removal, project encryption-secret storage/removal, manual connection/push/pull/history actions, and fail-closed automatic-sync enable/disable state. The ordinary Windows candidate UIA path uses only a localhost generic-S3 profile and proves profile persistence plus secret-field clearing/redaction without network egress; the protected live workflow separately drives the real provider UI path. These controls do not convert configuration into provider evidence.

Current release limits remain explicit. The routed cloud project-sync path now encrypts verified `.rwproj` bytes with the project-sized `RWPENC1` envelope (up to the 256 MiB archive bound) before handing the sealed object to the revision/CAS engine. `SyncService::push_sealed` and `pull_encrypted` are envelope-agnostic and accept the larger bounded object size; focused sync coverage includes a sealed object larger than the legacy 16,000,000-byte `RWENC1` plaintext ceiling, and cloud helper tests assert newly pushed project archives start with `RWPENC1`. Pull retains a legacy `RWENC1` fallback only so older remote revisions remain readable. Therefore the former 16 MB large-project sync blocker is superseded by the current code. Live Liara variables/secrets are still absent from the protected GitHub environment, so a real external provider connection/conditional-write probe/encrypted push-pull/second-device sequence has not been claimed.
